# Exporting

Every export runs through `ExportManager`, which produces an in-memory
`ExportBundle` (a list of files plus warnings). The platform layer is only
responsible for writing those files - to a folder or a `.zip` on desktop,
always to a `.zip` on Android, where there is no reliable cross-OEM "write a
folder tree" story.

A worked example of every output below lives in
[`templates/sample-output/`](../templates/sample-output), regenerated by
`./gradlew exportTemplates`.

---

## Java Edition resource pack

Vanilla Java has no data-driven screen format, so a faithful export is
necessarily two halves: the assets a pack can ship as-is, and a generated
`Screen` subclass that lays the widgets out exactly as designed.

```
custom_chest_java_pack/
├── pack.mcmeta
├── assets/mcgui/
│   ├── gui/custom_chest.json          ← portable layout description
│   ├── lang/en_us.json                ← a key per label in the screen
│   └── textures/gui/*.png             ← every texture you imported
├── src/main/java/com/example/mcgui/client/gui/
│   └── CustomChestScreen.java         ← ready-to-compile Screen subclass
└── README.md
```

### Using the pack half

Zip the *contents* of the folder (the level that contains `pack.mcmeta`) and
drop it into `.minecraft/resourcepacks`. Textures become available as
`mcgui:textures/gui/<file>.png`.

### Using the generated screen

1. Copy `CustomChestScreen.java` into your mod's source tree.
2. Fix the package statement if your mod does not use `com.example.<namespace>`.
3. `Minecraft.getInstance().setScreen(new CustomChestScreen())`.

The class centres the authored canvas in the window, so it behaves correctly at
every GUI scale. Widgets that map to real vanilla components (`Button`,
`EditBox`) are created in `init()`; everything else is drawn in `render()`. Each
button gets an `onXxx()` handler stub carrying its action id.

Regenerating overwrites the file wholesale - keep custom logic in a subclass.

### `gui/<screen>.json`

The portable half. Everything the generated Java does is derivable from this
file, which is what makes the export useful to mod loaders, KubeJS scripts or
your own runtime:

```jsonc
{
  "format": 1,
  "edition": "java",
  "screen": { "id": "custom_chest", "width": 176, "height": 166, "gui_scale": 3 },
  "textures": [ { "id": "...", "path": "mcgui:gui/panel.png", "nine_slice": {...} } ],
  "elements": [
    {
      "id": "...", "type": "button.normal", "x": 8, "y": 40, "width": 150, "height": 20,
      "properties": { "label": "Done", "background": "0xFF6C6C6C", "background_hex": "#6c6c6c" },
      "states": { "hover": { "background": "0xFF7F7F7F" } },
      "children": []
    }
  ]
}
```

Colours are emitted both as a Java `0xAARRGGBB` literal and as a `_hex` variant,
so neither a mod nor a web tool has to convert.

## Bedrock Edition resource pack

Unlike Java, Bedrock screens *are* data, so this export is directly loadable.

```
touch_hud_bedrock_pack/
├── manifest.json                      ← freshly generated UUIDs
├── ui/
│   ├── _ui_defs.json                  ← registers the screen with the game
│   ├── _global_variables.json         ← canvas + safe-area values
│   └── touch_hud.json                 ← the screen, one control per element
├── texts/en_US.lang
├── textures/ui/*.png
└── README.md
```

### Installing

1. Copy the folder into `com.mojang/development_resource_packs/`.
2. Enable it in the world's Resource Packs settings.
3. `/reload`, or re-enter the world.

On Windows, `com.mojang` lives under
`%LOCALAPPDATA%\Packages\Microsoft.MinecraftUWP_8wekyb3d8bbwe\LocalState\games\`.

### About the generated JSON UI

* The screen root inherits `common.base_screen`, so the pack keeps working with
  the rest of the UI (input handling, the back button, and so on).
* Positions use `anchor_from` / `anchor_to` / `offset`, so the layout scales
  with the player's chosen GUI size instead of being pinned to pixels.
* Designer elements map onto the closest native control type - `label`,
  `button`, `edit_box`, `slider`, `toggle`, `dropdown`, `scroll_view`, `image`.
  Anything without a native equivalent (inventory slots, the touchpad) becomes a
  `panel`/`custom` control carrying its designer type, ready to be bound to your
  own renderers. That is exactly what vanilla does for its own compound widgets.
* Keys beginning with `$designer_` are round-trip metadata and are ignored by
  the game.

## Code generation

The **Code** tab turns the current design into something you can paste
elsewhere. Every generator works from absolute canvas-space bounds, so the
output is flat and readable rather than a nest of relative offsets.

| Target | Output |
| --- | --- |
| **HTML + CSS** | A self-contained page with embedded textures as data URIs, `image-rendering: pixelated`, and real `:hover`/`:active`/`:focus` rules generated from the element's interaction states. Opens in any browser. |
| **CSS only** | The stylesheet on its own, one class per element, for dropping into an existing page. |
| **Kotlin (Compose)** | A `@Composable` reproducing the layout with `Box` + `offset` + `size`. |
| **Java (Minecraft Screen)** | The same source the Java pack ships. Java projects only. |
| **Bedrock JSON UI** | The same `ui/<screen>.json` the Bedrock pack ships. Bedrock projects only. |
| **Project document** | The raw `.mcgui`, for tooling that wants the model itself. |

## Cross-edition warnings

Both edition packs are always offered, whichever edition the project targets,
because porting a screen is a common reason to export. When you export for the
edition a project was *not* designed for, the bundle carries an explicit
warning listing every widget with no counterpart:

> This project targets Bedrock Edition but is being exported for Java Edition.
> 3 element(s) have no direct equivalent.

Those elements are still exported, as generic panels, so nothing is silently
dropped. The same information is available any time from
`ProjectValidator.parityIssues`, and the Issues panel shows it as notes.

## Validation before export

Exports run the validator in **strict** mode, which additionally reports
unknown properties. The bundle's `warnings` list is shown in the export dialog
before you commit, split into errors and warnings. Errors mean the pack will
not behave as designed - a missing texture, a duplicate id, an element that does
not exist in the target edition, an invalid namespace.

`./gradlew validateProjects` runs the same checks over every bundled template,
and CI fails the build on any error.
