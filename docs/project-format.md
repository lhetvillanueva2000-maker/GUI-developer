# The `.mcgui` project format

A project is a single JSON document. It is plain text so it diffs well in git
and can be generated by external tooling, and it is self-contained - imported
textures live inside it as base64, so moving a project between machines is one
file copy.

## Top level

```jsonc
{
  "formatVersion": 1,
  "id": "project_9k2mfa1x0d7q",
  "name": "Java Chest Container",
  "edition": "java",              // "java" | "bedrock"
  "canvas": { /* see below */ },
  "elements": [ /* ordered tree */ ],
  "textures": [ /* imported images */ ],
  "meta": { /* export identity */ }
}
```

`formatVersion` is checked on load. A document written by a newer build still
loads - unknown fields are ignored and a warning is surfaced - and
`ProjectSerializer.migrate` is where future upgrades go.

## Canvas

```jsonc
"canvas": {
  "width": 176,                  // GUI pixels, not screen pixels
  "height": 166,
  "guiScale": 3,                 // scale the live preview renders at
  "gridSize": 8,
  "backdrop": "DIM",             // NONE | DIM | GAME_WORLD | DIRT_PANORAMA | SOLID
  "backdropColor": 3221291032,
  "targetForm": "desktop",       // desktop | mobile
  "safeArea": { "left": 12, "top": 8, "right": 12, "bottom": 8 }
}
```

Everything is in **GUI pixels** - the unscaled Minecraft coordinate space where
a vanilla chest screen is 176 x 166. Nothing in the document is ever in screen
pixels, which is what makes a project render identically at every GUI scale and
on every device.

`safeArea` only matters for `targetForm: mobile`; the Bedrock preview draws it
and the validator warns about elements that reach into it.

## Elements

Elements form an ordered tree. **List order is z-order**: index 0 paints first
(furthest back), the last child paints last (on top).

```jsonc
{
  "id": "button_a1b2c3d4e5f6",
  "type": "button.normal",       // a key from ElementCatalog
  "name": "Confirm",
  "bounds": { "x": 8, "y": 40, "width": 150, "height": 20 },
  "anchor": "TOP_LEFT",
  "visible": true,
  "locked": false,
  "props": {
    "label":      { "kind": "s", "value": "Done" },
    "enabled":    { "kind": "b", "value": true },
    "background": { "kind": "c", "argb": 4285229931 }
  },
  "stateOverrides": {
    "HOVER": { "background": { "kind": "c", "argb": 4286545791 } }
  },
  "children": []
}
```

`bounds` is relative to the parent's content box, so moving a container moves
everything inside it.

### Property values

The `kind` discriminator keeps the format compact and self-describing:

| `kind` | Type | Payload |
| --- | --- | --- |
| `s` | String | `"value"` |
| `i` | Int | `"value"` |
| `f` | Float | `"value"` |
| `b` | Boolean | `"value"` |
| `c` | Colour | `"argb"`, packed `0xAARRGGBB` as a number |
| `e` | Enum choice | `"value"`, one of the spec's `options` |
| `tex` | Texture reference | `"assetId"`, or `null` for none |
| `l` | List | `"values"`, an array of the above |

### Interaction states

`stateOverrides` stores **only** the properties that differ from `props`, keyed
by `NORMAL` / `HOVER` / `PRESSED` / `FOCUSED` / `DISABLED`. A project that never
customises its hover state stays small. Bedrock projects only use
`NORMAL` / `PRESSED` / `DISABLED` - touch has no pointer to hover with.

### Anchors

`anchor` decides what happens when the parent (or canvas) is resized:
`TOP_LEFT` … `BOTTOM_RIGHT`, plus the centres. Java screens are typically
centred on the window; Bedrock screens are usually anchored to safe-area edges.

## Textures

```jsonc
"textures": [
  {
    "id": "tex_7h3k9d2m1p0s",
    "name": "custom_panel.png",
    "format": "png",
    "width": 32,
    "height": 32,
    "dataBase64": "iVBORw0KGgoAAAANSUhEUg...",
    "nineSlice": { "left": 4, "top": 4, "right": 4, "bottom": 4 },
    "pixelated": true,
    "sourcePath": "/home/me/art/custom_panel.png",
    "frameCount": 1,
    "frameTimeTicks": 2,
    "interpolate": false,
    "frameDelaysMillis": []
  }
]
```

`nineSlice` is what turns a small PNG into a stretchable panel or button skin:
the corners stay pixel-exact while the edges and centre stretch. All four at
zero means "stretch the whole image".

The four animation fields describe a frame strip. `frameCount` above 1 means
the PNG is `width` wide and `width * frameCount` tall, played top to bottom -
the format both editions animate natively, and what an imported GIF is
converted to. `frameTimeTicks` is the `frametime` written to the exported
`.mcmeta` (20 ticks to the second), and `interpolate` asks the game to
cross-fade between frames.

`frameDelaysMillis` keeps the source's own per-frame timings when it had
uneven ones. Minecraft has a single `frametime` per texture, so the resource
pack export writes explicit per-frame `time` entries to reproduce them
exactly; every other export uses one averaged rate, and the validator says so.

All four default to a still, so a document written before they existed loads
unchanged.

Deleting a texture in the app clears every reference to it, so a document can
never contain a dangling asset id.

## Meta

```jsonc
"meta": {
  "author": "",
  "description": "A vanilla-accurate three-row chest.",
  "createdAt": "",
  "modifiedAt": "",
  "tags": ["java", "container"],
  "namespace": "mcgui",          // assets/<namespace>/… on Java, JSON-UI namespace on Bedrock
  "screenId": "custom_chest"     // becomes <screenId>.json in both exports
}
```

`namespace` must match `^[a-z0-9_.-]+$`; the validator reports it as an error
otherwise, because both editions would reject the pack.

## Reading it from your own tooling

The format is stable and documented, but the least fragile way to consume a
project is to export it: `assets/<ns>/gui/<screen>.json` (Java) and
`ui/<screen>.json` (Bedrock) are both derived from the same document and are
designed to be read by other runtimes. See [exporting.md](exporting.md).
